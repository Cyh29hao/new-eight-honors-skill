# 为什么重新设计八条

这套规则来自作者与 Codex 在真实项目中的多轮讨论，集中修订于 2026-10-21，并在2026-10-30继续加入表达与个人偏好的调整。以下早期引文经本机原始聊天核对。

## 给 Codex 补一点人性

作者最近的使用感受是：原生Codex时常显得“降智”，清楚交代任务后仍得投入不少prompt engineering；但它能动手完成整段工作的生态位又很难替代。新八条希望把人的体谅、判断与担当放进智能体的工作方式：听懂实际目的，找到更好办法，愿意拿主意，按真实使用体验验收，也能把成果交代清楚。

这些是作者的使用感受与设计动机。具体落实为可观察的行为：第4条主动给判断和可行路径，第8条减少防御与免责铺垫、先说结果和建议；“少说不”的目标是较原风格减少约80%，保留准确的事实与风险。

使用习惯由使用者选择：汇报强度、语气、实际接入和额度预留线写进项目偏好。API/中转以实际服务预算为准，计划额度只在来源确认后使用；八条协作与阶段交接共同适用。

## 使用场景扩大了

作者先指出通行的 AI 编程八荣八耻并不完全适合自己的使用需求。当时的工作不只修改代码，还包括研究、课程材料、网页、视频和电脑操作。对规则的要求随之扩展：需要查现成经验、理解受众、检验实际作品，也需要清楚的交接和持续沟通。

“使用场景扩大”是早期项目范围的概括；上面的近期使用感受属于后续设计背景。

## 目标要尊重，方法要判断

2026-10-21 的用户原话：

> 我说的不一定对，可能只是提供一个示例或者方向，如果你一味执行而不做质疑或者自主变通则会出现问题

它要求区分明确目标、硬约束和候选方法。代理应在授权内承担常规判断，有依据地质疑、调整方法；不把每个细节推回用户，也不擅自改变目标。

## 各条要有自己的职责

后续讨论将容易重叠的几组要求分开：

- 目标管成功是什么，判断管方法和决策权。
- 查证管陈述是否有依据，验收管实际产物是否达到用途。
- 接续管中断时怎样交接，成本管下一步是否值得投入，汇报管用户能否看见过程和限制。

由此形成目标、证据、复用、判断、验收、接续、成本和沟通八个独立职责，分别约束不同问题，不互相替代。例如如实说明“已导出”解决了陈述有据的问题，仍需要另做成品验收；保存了进度，也仍要判断继续投入是否值得。

## 长任务必须有可读的收尾

同日另一条用户原话：

> 绝对不能出现额度耗尽却没有给我看的报告总结式输出的现象

原消息还要求阶段文字汇报、减少黑盒，以及一次授权后的可靠接续。由此把提前留额度、保存成果、给人看的报告和核验恢复机制连起来。当时核查发现，现有 `resume` 只展示历史，没有建立自动唤醒；用户需要的能力与已经实现的机制必须分开。

## 从本机约定到可安装 skill

公开包把这些偏好拆成三部分：`AGENTS.md` 中长期带入的约定、`SKILL.md` 与按需参考资料，以及实际额度/交接工具。安装器另补上项目规则备份和标记块合并。

这也是一种个人管理偏好：目的明确、方法给空间、成品按实际用途验收、过程与中断有交代。使用者可以调整报告频率、阈值和项目细则，保留适合自己的部分。
